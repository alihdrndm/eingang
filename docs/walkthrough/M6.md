# M6 — Evaluation: does the extraction work, and does validation agree with KoSIT?

## What was built

- **The dataset** (`evals/build_dataset.py`): 104 hybrid ZUGFeRD/Factur-X invoices from the pinned corpus. The truth for each is its own embedded XML, parsed by the same parser as the app; the input is the PDF's text layer, extracted as the app extracts it. Identical PDFs count once.
- **Two systems over the same text** (`evals/run_extraction.py`): a label-anchored regex baseline (free) and the application's own LLM extraction, through the same client, prompt, budgets and grading as production. The LLM run prints its estimate, asks for `yes`, stops before `EVAL_BUDGET_USD` and allows two live runs per prompt version.
- **Metrics** (`evals/metrics.py`): per field accuracy, hallucination and abstention; per document "critical fields correct" (number, issue date, gross total and the IBAN when there is one) with a seeded bootstrap interval.
- **Validation parity** (`evals/parity.py`): Eingang's verdicts against the official KoSIT validator, run in Docker on the XRechnung test suite and every corpus XML.
- **Publishing:** each run writes a dated Markdown and JSON report and merges into `evals/latest.json`, which the API serves at `/accuracy` and the README quotes.

## Results

- **LLM (`gpt-5-nano`, minimal reasoning): 65.4%** of invoices with every critical field right (95% CI 56.7–74.0%), for $0.0334 recorded plus about $0.0003 for one failed call the ledger lost, $0.000321 per invoice, about 4.7 s each.
- **Regex baseline: 21.2%** (13.5–28.8%).
- **Parity: 100%** verdict and fatal-rule agreement on 176 files. Of 64 excluded, 49 have no KoSIT scenario (every BASIC and EXTENDED file among them), 14 are profiles Eingang doesn't accept and 1 is not an invoice.

## Key decisions

1. **The truth is the embedded XML, and its limits are reported.** A PDF can print an IBAN its XML leaves out. The report counts such a value as a hallucination, and `docs/EVALS.md` says that 15 of the 17 counted IBANs are printed (one is a GLN read as an IBAN, one the text "null"). It also says the 104 documents are only 33 distinct invoices, so the intervals are narrower than the data supports. A favourable reading is never put into the headline number.
2. **The evaluation uses the production path, not a copy.** The run goes through `llm/client.py`, so it is budgeted, cached and in the ledger. This paid off at once: one answer contained a NUL character, which PostgreSQL refuses, and the failed cache write rolled back that call's ledger row. Production would have crashed and retried the same way. The fix (clean answers, cache write in a savepoint) landed before this milestone closed, and the lost call (about $0.0003) is stated in `docs/COSTS.md`.
3. **The baseline's tuning is disclosed.** Its labels were extended after looking at the corpus (3.8% → 21.2%), which favours the baseline, not the LLM.
